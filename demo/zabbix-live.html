timeseries.js — Zabbix live

problems and items in two tabs — one shared, synchronised time viewport

Careful: the API token you enter is stored in clear text in localStorage, so that a reload keeps the connection. It is therefore readable by every script on this origin — and on a shared host such as GitHub Pages that origin covers every other page served from it — and it survives a browser restart. So: use a read-only Zabbix API user, and revoke the token server-side once you no longer need it. “Disconnect” only forgets it locally.

The URL has to be the JSON-RPC endpoint, i.e. …/api_jsonrpc.php — not …/zabbix.php, which is the frontend. API tokens are created in Zabbix under Users → API tokens; a read-only user is entirely sufficient for this page. The credentials are only stored after a successful, real API call — see the note above for where they end up. If the connection fails with a network/CORS error, the message names the headers you need; the long explanation is in the Items tab once connected.

Draws every Zabbix problem in the currently visible window as a gantt bar (one lane per host). The history comes from event.get (value: 1, i.e. each PROBLEM event individually — not problem.get, which only mirrors Zabbix' current problem view and drops older repetitions of the same trigger); problems still open, of any age, are fetched additionally from problem.get with recent: false. Open problems run up to “now”, resolved ones up to their recovery time — which is not in the event.get response (r_clock only exists on problem.get) and has to be looked up via r_eventid as the clock of the corresponding OK event. Host names for the problem.get rows are likewise looked up via the trigger id (objectid), since problem.get has no selectHosts. Repetitions of one trigger share a row via group instead of scattering across the lane. The host selection filters purely client-side out of the events already loaded (hence instantly, with no request, and with each host's problem count in brackets); All hosts clears the filter and is mutually exclusive with picking individual ones. Refreshes on every pan/zoom and, as long as the window touches the leading edge, automatically every 20 s. Colour = severity (legend above). The Items tab shares this viewport (the group option) — panning/zooming here moves it along, even while it is invisible.

Pick a host, then an item — only numeric items (float/unsigned) can be drawn as a history/trends band, so text/log/char items are filtered out of the list. Any number of items can be added; each gets its own colour and appears as its own series in the same history/trends band (cross-fading on zoom just like the plain zabbix source). The legend in the chart's top right hides an item; the × on its chip removes it entirely. Mind the scale: all items share one linear y-axis — items of very different magnitude (say a percentage next to a byte counter) should not be added at the same time, or the smaller one vanishes visually next to the larger.

CORS: jpZabbix.js sends Content-Type: application/json and (since Zabbix 6.4/7.0, where the auth parameter is no longer allowed in the body) the API token as an Authorization: Bearer … header. Together those are not a “simple request”, so every call triggers an OPTIONS preflight. For this page to work from a different origin, the web server in front of api_jsonrpc.php must answer OPTIONS with at least Access-Control-Allow-Origin (this page's origin, or *), Access-Control-Allow-Methods: POST, OPTIONS and Access-Control-Allow-Headers: Content-Type, Authorization. An Access-Control-Allow-Headers: * is not enough: per the Fetch specification a wildcard explicitly excludes the Authorization header — it has to be named in the list, or the request hangs in the browser / is rejected as a CORS error.
